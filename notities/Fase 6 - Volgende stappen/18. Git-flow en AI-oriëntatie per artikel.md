## Git-flow

### Wat het is
Een vaste manier om branches te gebruiken:

| Branch | Waarvoor |
|---|---|
| `main` | Alleen releases. Wat hier staat, is af |
| `develop` | Integratie: afgeronde features komen hier samen |
| `feature/…` | Eén nieuwe functie, vanaf `develop` |
| `bugfix/…` | Een fout in `develop`, vanaf `develop` |
| `release/…` | Een versie klaarmaken: van `develop` naar `main` |
| `hotfix/…` | Een fout in `main` die niet kan wachten |

Tot nu toe werkte ik direct op `main`. Met git-flow staat op `main` alleen werk dat klaar is, en kan ik halverwege een feature stoppen zonder dat `main` kapot is.

### Installeren
Git for Windows 2.55 heeft geen `git flow` meer ingebouwd. De opvolger is `git-flow-next` van Tower:

```powershell
winget install GitTower.GitFlowNext
```

Daarna in de repo:

```bash
git flow init --preset=classic --defaults
git push -u origin develop
```

`--preset=classic` geeft de indeling uit de tabel hierboven, `--defaults` neemt de standaardnamen zonder te vragen.

### Een bugfix tussendoor
Bij het starten van de feature faalde `ArticleImagesTest`. De test had een vaste datum, en die viel inmiddels buiten het Hot-venster van 48 uur. De test was dus afhankelijk van de dag waarop ik hem draaide.

Dat is geen onderdeel van de AI-feature, dus een eigen bugfix-branch:

```bash
git flow bugfix start test-datums
# in de test: $this->travelTo('2026-10-12 18:00:00');
git flow bugfix finish test-datums
```

`travelTo()` zet de klok van Laravel (`now()`) op een vast moment, alleen tijdens de test. `finish` merget de bugfix naar `develop` en verwijdert de branch.

### Feature bijwerken: rebase en force-with-lease
De feature branch was gestart vóór de bugfix. Om de fix ook in de feature te hebben:

```bash
git flow feature update
git push --force-with-lease
```

`feature update` doet een rebase: mijn feature-commits worden opnieuw bovenop de nieuwe `develop` gezet. Daarbij krijgen ze nieuwe hashes. GitHub had nog de oude commits, dus een gewone `push` wordt geweigerd.

- `--force` overschrijft de branch op GitHub, wat er ook staat.
- `--force-with-lease` overschrijft alleen als de branch op GitHub nog is wat ik de laatste keer heb opgehaald. Heeft iemand (of ik op de laptop) er intussen iets op gezet, dan weigert hij. Zo gooi ik nooit per ongeluk andermans werk weg.

> [!note] Rebasen is prima op een branch waar alleen ik op werk. Op `develop` of `main` nooit: dan veranderen commits die anderen al hebben.

## AI-oriëntatie per artikel

### Kolommen
Op `artikelen`, allemaal `nullable`, want een artikel zonder schatting is normaal:

```php
$table->string('ai_orientatie')->nullable()->after('embedding');
$table->unsignedTinyInteger('ai_zekerheid')->nullable()->after('ai_orientatie');
$table->text('ai_onderbouwing')->nullable()->after('ai_zekerheid');
$table->string('ai_model')->nullable()->after('ai_onderbouwing');
$table->timestamp('ai_geschat_op')->nullable()->after('ai_model');
```

Later een tweede migratie voor `ai_politiek` (boolean), zie hieronder.

- `ai_orientatie` gebruikt dezelfde 5 labels als MBFC (`left` … `right`). Dan kan ik ze direct vergelijken met `bronnen.orientatie`.
- `ai_model` en `ai_geschat_op`: welk model en wanneer. Hetzelfde idee als `samenvattingen.model` in bouwblok 17.
- `unsignedTinyInteger` is 0 t/m 255, genoeg voor 0–100. Dat `unsigned` gaf later een bug.

### Service `OrientatieSchatter`
Zelfde opzet als `ArtikelVergelijker` (notitie 4): een systeemprompt, een `json_schema` als `response_format`, en daarna zelf alles valideren.

Wat **niet** in de prompt staat: de bronnaam en het MBFC-label. Anders kijkt het model naar "Breitbart" en zegt `right`, en meet ik alleen of het model MBFC kent.

```php
$bericht = "Titel: {$artikel->titel}\nTekst: {$tekst}";
```

Het schema met een `enum`, zodat het model alleen bekende labels kan kiezen:

```php
'orientatie' => ['type' => 'string', 'enum' => self::LABELS],
```

Het model houdt zich niet altijd aan het schema. Daarom per veld een controle, met een `RuntimeException` als iets niet klopt. Het command vangt die op en probeert het opnieuw.

### Command `artikelen:orientatie-schatten`
```bash
php artisan artikelen:orientatie-schatten --limit=20
php artisan artikelen:orientatie-schatten --bron="The Guardian: World"
php artisan artikelen:orientatie-schatten --opnieuw
```

- Nieuwste artikelen eerst, alleen die zonder schatting (tenzij `--opnieuw`).
- `--limit=20` als standaard: elk artikel is een AI-call. Per ongeluk 5000 artikelen schatten kost tijd en geld.
- 3 pogingen per artikel. Na 3 keer een ongeldig antwoord of geen verbinding: overslaan, de rest gaat door.
- Niet in de scheduler. Dit is een meting, niet iets wat elk uur moet.

## Bijsturen na de eerste 5 schattingen
De eerste versie vroeg alleen om oriëntatie en zekerheid. Na 5 artikelen zag ik het probleem: een wedstrijdverslag en een kwartaalcijfer kregen `neutral` met 90% zekerheid.

Dat klopt op zich (er is niks links of rechts aan sport), maar het zou elke bron naar het midden trekken. Een linkse krant met veel sportnieuws zou dan "Midden" worden. En 90% zekerheid zei iets anders dan ik wilde weten: het model was zeker dat er geen kleuring was, niet over een richting.

Twee aanpassingen:

**1. Een veld `politiek_geladen`.** Gaat het artikel over een onderwerp waarover links en rechts verschillend denken? Zo niet, dan `neutral` en telt het niet mee voor de bron.

**2. Zekerheid gaat over de richting.** In de prompt:

```php
.'zekerheid: een geheel getal van 0 tot 100: hoe zeker ben je over de richting van de oriëntatie. '
.'Dit gaat niet over hoe zeker je bent dat er weinig kleuring is. '
.'Geef hooguit 40 als politiek_geladen false is of als de tekst korter is dan ongeveer 300 tekens, '
```

Het model hield zich niet altijd aan die 40. Daarom dwingt de code hem af:

```php
$weinigAanwijzingen = ! $data['politiek_geladen'] || mb_strlen($tekst) < self::MINIMALE_TEKSTLENGTE;

'zekerheid' => $weinigAanwijzingen ? min($data['zekerheid'], 40) : $data['zekerheid'],
```

> [!note] Een regel in de prompt is een verzoek, geen garantie. Wat echt moet kloppen, controleer ik in PHP.

Ook in de prompt: beoordeel hoe het artikel geschreven is (woordkeuze, wie dader of slachtoffer is, wat wordt weggelaten), niet het onderwerp. Een artikel over migratie is niet vanzelf rechts.

De 5 oude schattingen hebben `ai_politiek = null`. Die tellen als politiek geladen; ze kunnen opnieuw met `--opnieuw`.

## Op de site

### Per bron: gewogen gemiddelde
`Bron::aiSchatting()` geeft per label een score, van `left` = -2 tot `right` = +2, en weegt elk artikel naar zijn zekerheid. Een artikel met 80% telt twee keer zo zwaar als een met 40%.

```php
$gewogen = $perLabel->sum(fn (object $rij): int => (int) $rij->gewicht * (array_search($rij->ai_orientatie, OrientatieSchatter::LABELS, true) - 2));
$score = $gewicht > 0 ? $gewogen / $gewicht : 0.0;
```

`array_search` geeft de positie in `LABELS` (0 t/m 4); min 2 maakt daar -2 t/m +2 van. De afgeronde score wordt weer een label.

Op de bronpagina staat een kaart "AI-schatting" naast "Politiek label (MBFC)", met het aantal artikelen en de gemiddelde zekerheid. Valt de schatting in een ander bakje dan MBFC: "Wijkt af van MBFC".

### Bug: unsigned in MySQL
Mijn eerste versie deed het wegen in de query zelf: zekerheid keer score, opgeteld met `SUM`. In de tests (SQLite) werkte dat. Op de echte database (MySQL) ging het mis. `ai_zekerheid` is `unsigned`, en in MySQL blijft unsigned keer een negatief getal unsigned. -2 × 60 past daar niet in, dus een overflow.

Oplossing: SQL telt alleen per label (`COUNT(*)`, `SUM(ai_zekerheid)`), en het vermenigvuldigen met de negatieve score gebeurt in PHP.

> [!warning] De tests draaien op een andere database dan de app. Groen in SQLite zegt niks over MySQL-specifiek gedrag. Database-werk daarom ook op de echte data controleren. Staat nu ook in de README.

### Per artikel
Een partial `ai-orientatie.blade.php` op de detailpagina, `/artikelen` en de bronpagina. Bij de bronnaam staat `MBFC: left-center`, daaronder een uitklapbaar label:

```blade
<details class="mt-2 text-xs text-muted">
    <summary>… AI: {{ $artikel->ai_orientatie }} · zekerheid {{ $artikel->ai_zekerheid }}%</summary>
    <p>{{ $artikel->ai_onderbouwing }}</p>
</details>
```

`<details>` en `<summary>` klappen open en dicht zonder JavaScript. Het bolletje heeft de kleur van het AI-bakje; "geen politieke lading" krijgt alleen een randje.

`Artikel::aiBakje()` geeft Links, Midden, Rechts, Geen lading, of `null` zonder schatting. De indeling zelf hergebruikt `Bron::bakjeVan()`, die ik daarvoor uit `bakje()` heb gehaald.

### `/over`
Een blok "AI-schatting per artikel, als toets": wat het model wel en niet ziet, dat artikelen zonder lading niet meetellen, en dat het model alleen de korte RSS-tekst krijgt.

## Toetsen: `orientatie:vergelijken`
Een command dat alleen de database leest, geen AI-calls:

```bash
php artisan orientatie:vergelijken
php artisan orientatie:vergelijken --min=3
```

Drie tabellen:

1. **Per bron**: MBFC, AI, de afwijking (AI-score min MBFC-score, -4 tot +4) en of het bakje hetzelfde is. Grootste afwijking eerst.
2. **Overeenstemming per MBFC-bakje**: bij hoeveel bronnen komt de AI in hetzelfde bakje uit.
3. **Confusion matrix per artikel**: rij = MBFC-bakje van de bron, kolom = AI-bakje van het artikel.

`--min` laat bronnen met te weinig artikelen weg. The Sun stond eerst bij de afwijkers door één foute schatting (kritiek op Labour-politicus Burnham werd `left-center`).

De matrix is per artikel en per rij, met opzet. Zo kan ik binnen de MBFC-rechtse bronnen kijken wat de AI doet, los van hoeveel rechtse bronnen ik heb. Dat haalt de twee verklaringen voor 116 tegen 52 uit elkaar.

### Uitkomst
Per bakje (68 bronnen):

| MBFC | Bronnen | Zelfde bakje | Gem. afwijking |
|---|---|---|---|
| Links | 39 | 38% | +0,9 |
| Midden | 10 | 80% | -0,3 |
| Rechts | 19 | 47% | -1,2 |
| Totaal | 68 | 47% | +0,1 |

Per artikel:

| MBFC \ AI | Links | Midden | Rechts | Geen lading |
|---|---|---|---|---|
| Links | 95 | 141 | 6 | 108 |
| Midden | 6 | 25 | 0 | 31 |
| Rechts | 16 | 63 | 46 | 77 |

Wat ik eruit haal:

- **Het model trekt alles naar het midden.** Linkse bronnen schuiven gemiddeld +0,9, rechtse -1,2. Midden klopt het vaakst (80%), maar dat is ook de kant waar het model toch al heen trekt.
- **Rechts wordt iets sterker naar het midden getrokken dan links.** En bij MBFC-rechtse bronnen schat de AI 16 artikelen links (13% van de geladen artikelen), bij MBFC-linkse bronnen maar 6 rechts (3%).
- **De scheefheid van 116 tegen 52 komt vooral door de bronnenmix**: 350 artikelen van linkse tegen 202 van rechtse bronnen. Daarbovenop zit een lichte trek naar links. Bias van DeepSeek is daarmee niet bewezen, maar ook niet uitgesloten.

> [!note] Zonder de matrix per MBFC-groep had ik "het model is links" of "mijn bronnen zijn links" geconcludeerd. Het is allebei een beetje, en de meting laat zien hoeveel.

## Beperkingen en open punten
- Het model ziet alleen de RSS-omschrijving, niet het hele artikel. Daardoor veel `neutral`.
- MBFC beoordeelt een redactie (ook onderwerpkeuze); de AI één tekst. Ze meten niet hetzelfde. Een afwijking is een aanwijzing, geen fout van één van de twee.
- De steekproef is scheef: nieuwste eerst, dus veelpublicerende bronnen tellen zwaarder. 51 bronnen hebben geen schatting.
- Bronnen met 1 of 2 artikelen zeggen weinig; gebruik `--min`.
- Bias van DeepSeek is niet uitgesloten. Een tweede model op dezelfde artikelen zou dat kunnen laten zien.
- 5 oude schattingen zonder `ai_politiek`.
- De zekerheid is een zelfinschatting van het model, geen statistische kans.
