Twee dingen vielen op:

En een derde, per ongeluk: 83 regels met `prompt_tokens: 10`. Dat zijn de tests. `Http::fake()` bootst de AI na, maar `Log::info()` schreef gewoon in de echte log. Opgelost in `phpunit.xml`:

```xml
<env name="LOG_CHANNEL" value="null"/>
```

> [!note] Een meting is pas iets waard als er geen nepdata tussen zit. Eerst de log schoon, dan pas conclusies.

## Hoe caching werkt in de keten

```
MediaLens ──► LiteLLM (Educom) ──► OpenRouter ──► provider (SiliconFlow, GMICloud, …) ──► DeepSeek V4 Flash
```

Er zijn drie plekken waar iets gecachet kan worden, en ze doen elk iets anders:

| Waar | Wat | Helpt bij |
|---|---|---|
| Provider (DeepSeek-model) | **Prefix-cache**: het begin van de prompt dat gelijk is aan een eerdere prompt, tegen 10% van de inputprijs. Automatisch, geen `cache_control` nodig | Een vast begin (systeemprompt, dezelfde artikelen) |
| OpenRouter | Kiest per aanroep een provider. **Sticky routing**: blijft bij dezelfde provider na een cache-hit, of meteen met een `session_id`. Vervalt na 10 minuten zonder aanvragen | Zorgen dat de prefix-cache bij dezelfde provider ligt |
| LiteLLM (Educom) | **Response-cache**: precies dezelfde vraag geeft hetzelfde bewaarde antwoord | Alleen identieke aanroepen. Staat op de proxy van Educom, niet in onze code |

Het probleem zit in de middelste. Elke provider heeft een eigen cache. Kiest OpenRouter voor de tweede aanroep een andere provider, dan is die cache koud, ook al is de prompt identiek.

`cache_control` (met `ephemeral`) ken ik van Anthropic. Dat is expliciete caching: je zegt zelf waar de cache eindigt. DeepSeek doet het automatisch; die parameter heeft daar geen zin.

## Proefaanroepen
Documentatie is één ding; wat de proxy van Educom echt doorgeeft, moest ik testen. Een klein script via Tinker: de artikelen van gebeurtenis 38 (±530 tokens) plus de vraag "hoeveel artikelen zijn het?", een paar keer achter elkaar. Tien aanroepen, samen minder dan een tiende cent.

### `session_id`

| Aanroep | Provider | Uit cache | Promptkosten |
|---|---|---|---|
| Zonder `session_id` | SiliconFlow | 0 | $0,000069 |
| Zelfde, nog een keer | SiliconFlow | 0 | $0,000071 |
| Met `session_id` | GMICloud | 0 | $0,000048 |
| Zelfde, nog een keer | GMICloud | **441 van 532** | **$0,000016** |

Met `session_id` kwam de herhaling voor 83% uit de cache, en de promptkosten daalden met 66%. LiteLLM geeft `session_id` dus door aan OpenRouter. Ook zichtbaar: dezelfde vraag is bij GMICloud goedkoper dan bij SiliconFlow.

### De denkinstellingen deden niets
Sinds bouwblok 5 stuurde `LiteLlm` de DeepSeek-parameters mee:

```php
'thinking' => ['type' => config('services.litellm.thinking_type')],
'reasoning_effort' => config('services.litellm.reasoning_effort'),
```

In notitie 5 schreef ik al: of die aankomen, zie je niet aan een 200, wel aan `reasoning_tokens`. Nu getest:

| Instelling | Denk-tokens | Output-tokens | Antwoord |
|---|---|---|---|
| `thinking: disabled` | 76 | 80 | 8 |
| Geen parameters | 90 | 94 | 8 |
| OpenRouter `reasoning: {effort: high}` | 115 | 119 | 8 |
| OpenRouter `reasoning: {enabled: false}` | **0** | **2** | **7** (fout) |

`thinking: disabled` gaf net zoveel denk-tokens als helemaal niks meesturen. Die parameter kwam dus niet aan. OpenRouter heeft een eigen parameter, `reasoning`, en die werkt wel.

Twee lessen:

- **Bijna alle output is denken.** Voor een antwoord van één getal 241 van de 244 tokens. Daar zit het geld, niet in de input.
- **Denken uit is goedkoper, maar niet gratis.** Zonder denken was het antwoord fout. Voor een samenvatting kan dat anders uitpakken dan voor tellen, maar dat moet een experiment uitwijzen, geen gok.

> [!warning] Een parameter die de proxy accepteert, is niet een parameter die aankomt. Altijd controleren aan iets wat verandert (hier `reasoning_tokens`).

## Wat ik veranderd heb

### `session_id` per soort en per uur
```php
'session_id' => "medialens-{$soort}-".now()->format('YmdH'),
```

Alle samenvattingen van één run delen een sessie, alle oriëntatieschattingen ook. Binnen een run blijven ze bij één provider, zodat de systeemprompt (en bij een gebeurtenis die opnieuw wordt samengevat: de eerdere artikelen) uit de cache kan komen.

Het uur zit erin omdat sticky routing na 10 minuten toch vervalt. De volgende run (een uur later) mag een nieuwe sessie zijn.

### Artikelen in vaste volgorde
```php
$gebeurtenis->load(['artikelen' => fn ($query) => $query->orderBy('id'), 'artikelen.bron']);
```

De prefix-cache werkt alleen op het **begin** van de prompt. Komt er een artikel bij een gebeurtenis, dan wordt die opnieuw samengevat. Staan de artikelen oudste eerst, dan komt het nieuwe artikel achteraan, en is alles ervoor gelijk aan de vorige keer: dat stuk kan uit de cache komen. Zonder vaste volgorde kan MySQL ze in een andere volgorde teruggeven, en is de prefix na het eerste verschil weg.

De test daarvoor kijkt niet naar de volgorde zelf, maar naar het gevolg:

```php
$voor = $vergelijker->artikelenTekst($gebeurtenis);
$this->artikel($bron, $gebeurtenis, 'Derde artikel');
$na = $vergelijker->artikelenTekst($gebeurtenis);

$this->assertStringStartsWith($voor, $na);
```

Zet iemand later iets veranderlijks vooraan (een datum, een telling), dan faalt deze test.

### `reasoning` in plaats van `thinking`
In `config/services.php`, per soort aanroep:

```php
'reasoning' => [
    'standaard' => (string) env('LITELLM_REASONING_EFFORT', ''),
    'samenvatting' => (string) env('LITELLM_REASONING_SAMENVATTING', env('LITELLM_REASONING_EFFORT', '')),
    'categorie' => (string) env('LITELLM_REASONING_CATEGORIE', env('LITELLM_REASONING_EFFORT', '')),
    'orientatie' => (string) env('LITELLM_REASONING_ORIENTATIE', env('LITELLM_REASONING_EFFORT', '')),
],
```

En in `LiteLlm` omgezet naar wat OpenRouter verwacht:

```php
return match ($instelling) {
    '' => null,                       // niks meesturen: standaard van de provider
    'uit' => ['enabled' => false],
    default => ['effort' => $instelling],
};
```

Per soort, omdat een samenvatting iets anders vraagt dan een classificatie (oriëntatie, categorie). Welke instelling per soort het beste is, staat nog open: dat is het experiment.

> [!note] `LITELLM_REASONING_EFFORT=high` in mijn `.env` werkt nu wél. Dat is iets duurder dan de standaard (±115 tegen ±90 denk-tokens). Wil ik het oude gedrag tot het experiment, dan maak ik die regel leeg.

### De log
Per aanroep nu ook:

| Veld | Waarom |
|---|---|
| `soort` | Samenvatting, categorie of oriëntatie apart kunnen optellen |
| `provider` | Welke provider OpenRouter koos: zie je of sticky routing werkt |
| `duur_ms` | Snelheid meten, niet alleen kosten |
| `reasoning_tokens` | Hoeveel van de output denken is |
| `cache_write_tokens` | Wat er in de cache is gezet |
| `kosten_totaal` + `kosten_bron` | De echte kosten uit `usage.cost` van OpenRouter; alleen zonder dat veld de schatting uit `.env` |

De oude schatting rekende met één prijs, terwijl providers verschillende prijzen hebben. `usage.cost` is wat OpenRouter echt rekent.

Bij het herschrijven ook bevinding C3 uit `ANALYSE.md` opgeruimd: `$systeem !== null` was altijd waar (het is een `string`), URL en key werden een tweede keer uit `config()` gelezen, en `$errorBody` werd niet gebruikt.

## Beperkingen en open punten
- `session_id` helpt binnen een run. Tussen twee runs (een uur) vervalt sticky routing, dus de cache van het vorige uur raakt alleen als OpenRouter toevallig dezelfde provider kiest. `provider.order` (een vaste voorkeursprovider met terugval) kan dat oplossen; nog niet getest of LiteLLM dat doorgeeft.
- De beste denkinstelling per soort is nog niet gekozen. Daarvoor een experiment op een vaste steekproef: tokens, duur, kosten én kwaliteit.
- De voor- en nameting moet nog: een paar runs met de nieuwe code, en dan dezelfde optelling als hierboven.
- Grote gebeurtenissen sturen nog steeds alle artikelen mee (D3) en `samenvattingen:genereren` loopt nog alle gebeurtenissen langs (S1).
- De proefaanroepen zijn een handvol aanroepen op één gebeurtenis. Ze laten zien wát er gebeurt, niet hoe vaak.
