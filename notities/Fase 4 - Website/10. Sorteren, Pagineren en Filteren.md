#laravel #cheatsheet #medialens

Uitleg voor mezelf van wat ik gedaan heb bij bouwblok 10 van de MediaLens casus: het overzicht sorteren op nieuwste artikeldatum, pagineren, en filteren op wel of geen samenvatting via de URL.

## Sorteren: withMax, niet updated_at
`get()` gaf geen vaste “nieuwste eerst”-volgorde. De README noemt twee opties: `updated_at` van de gebeurtenis, of de hoogste `artikelen.publicatiedatum`.

`updated_at` op `gebeurtenissen` beweegt niet als de matcher een artikel aan een bestaande groep koppelt. In `GebeurtenisMatcher` wordt alleen het artikel geüpdatet (`gebeurtenis_id`). De rij in `gebeurtenissen` blijft ongemoeid. Voor een nieuwsoverzicht is de publicatiedatum van het nieuwste artikel de juiste knop.

`withMax` is hetzelfde soort Eloquent-hulpje als `withCount` en `withExists` uit bouwblok 6. Laravel voegt `artikelen_max_publicatiedatum` toe. Daarna sorteer ik daarop.

```php
->withMax('artikelen', 'publicatiedatum')
->orderByDesc('artikelen_max_publicatiedatum')
```

**Laravel-concept:** `withMax('relatie', 'kolom')` maakt de naam `relatie_max_kolom`. Zelfde patroon als `withCount('artikelen')` dat `artikelen_count` maakt. `latest()` zou op `created_at` van de gebeurtenis zelf sorteren; die shortcut past hier niet.

`has()`, de `withCount`s en de rest van de query blijven. De Blade-view toont de datum niet. Ik controleer de volgorde, niet een nieuw veld op het scherm.

## Gelijkspel op dezelfde dag
Eerste check: de pagina begon met een ander onderwerp dan phpMyAdmin, terwijl beide op `MAX(publicatiedatum) DESC` sorteerden. Alle rijen van 9 oktober hadden `2026-10-09`.

`publicatiedatum` is een `date` in de migratie, geen tijdstip. `orderByDesc` op die kolom zegt alleen: nieuwste dag eerst. Binnen die dag mag MySQL de volgorde zelf kiezen. Laravel en phpMyAdmin kozen allebei iets anders.

Tweede `orderBy` als tiebreaker:

```php
->orderByDesc('artikelen_max_publicatiedatum')
->orderByDesc('id')
```

Laravel-conventie: je mag `orderBy` stapelen. SQL wordt `ORDER BY … DESC, id DESC`. De phpMyAdmin-check moet dezelfde tweede kolom hebben, anders vergelijk ik weer twee andere volgordes:

```sql
SELECT g.id, g.onderwerp, MAX(a.publicatiedatum) AS nieuwste
FROM gebeurtenissen g
JOIN artikelen a ON a.gebeurtenis_id = g.id
GROUP BY g.id, g.onderwerp
HAVING COUNT(a.id) >= 2
ORDER BY nieuwste DESC, g.id DESC
LIMIT 5;
```

> [!note] Twee verschillende USS Lincoln-onderwerpen in de top zijn twee groepen, geen sorteerfout. Dat is de matcher.

## Pagineren: paginate in plaats van get
`get()` haalt alle groepen met 2+ artikelen in één keer op. `paginate(15)` laat de database twee dingen doen: het totaal tellen, en alleen 15 rijen van de huidige pagina ophalen. Laravel leest het paginanummer uit `?page=2`. Geen JavaScript.

```php
->orderByDesc('artikelen_max_publicatiedatum')
->orderByDesc('id')
->paginate(15);
```

`paginate` vervangt `get`, het is geen extra regel erna. `@foreach` blijft hetzelfde. Een paginator gedraagt zich in de loop als een collectie.

In de view, ná de `</ul>`:

```blade
{{ $gebeurtenissen->links() }}
```

`links()` is een methode op de paginator, niet op een model. Laravel tekent Vorige / 1 / 2 / Volgende. Die view zit in het framework.

Check: pagina 1 heeft 15 onderwerpen. `?page=2` is dezelfde 15 rijen als phpMyAdmin met `LIMIT 15 OFFSET 15` en dezelfde `ORDER BY`. Groepen met 1 artikel blijven buiten de telling door `has('artikelen', '>=', 2)`.

## Filter via de querystring
In notitie 6: `withExists('samenvatting')` zet alleen het vinkje. `has('samenvatting')` **filtert**. Dat tweede gebruik ik nu bewust, plus het omgekeerde: `doesntHave`.

Laravel-concept: `Request` in de methodesignature. Zelfde idee als route model binding bij `show(Gebeurtenis $gebeurtenis)`: ik typ het type, Laravel vult het in. `$request->query('filter')` leest `?filter=zonder` uit de URL. `use Illuminate\Http\Request;` stond al bovenaan de controller.

`paginate(15)` moet in twee stukken: eerst de query bouwen, dan eventueel extra filteren, dan pas pagineren.

```php
public function index(Request $request)
{
    $filter = $request->query('filter');

    $query = Gebeurtenis::has('artikelen', '>=', 2)
        ->withCount([ /* dezelfde tellingen als notitie 9 */ ])
        ->withMax('artikelen', 'publicatiedatum')
        ->orderByDesc('artikelen_max_publicatiedatum')
        ->orderByDesc('id');

    if ($filter === 'met') {
        $query->has('samenvatting');
    } elseif ($filter === 'zonder') {
        $query->doesntHave('samenvatting');
    }

    $gebeurtenissen = $query->paginate(15)->withQueryString();

    return view('gebeurtenissen.index', [
        'gebeurtenissen' => $gebeurtenissen,
    ]);
}
```

De drempel van 2 artikelen blijft altijd, ook bij een filter. Onbekende waarden (`?filter=foo`) vallen door de `if` heen en gedragen zich als Alle.

`withQueryString()` hoort bij de paginator. Zonder die aanroep wordt pagina 2 `?page=2` en valt `filter=zonder` weg.

## Links in Blade, geen JavaScript
Onder de `h1`, vóór de lijst:

```blade
<p class="mt-4 space-x-4 text-sm">
    <a href="{{ route('gebeurtenissen.index') }}" class="text-blue-800 underline">Alle</a>
    <a href="{{ route('gebeurtenissen.index', ['filter' => 'met']) }}" class="text-blue-800 underline">Met samenvatting</a>
    <a href="{{ route('gebeurtenissen.index', ['filter' => 'zonder']) }}" class="text-blue-800 underline">Zonder samenvatting</a>
</p>
```

`filter` zit niet in de route `/gebeurtenissen`. Extra keys in `route()` worden dan querystring. Dat is een Laravel-conventie.

De named route `gebeurtenissen.index` wijst naar `/gebeurtenissen`, niet naar `/`. Filterlinks horen die naam te gebruiken, anders land ik op `/?filter=zonder`. `/` blijft zonder naam, zie notitie 8.

Check: `/gebeurtenissen?filter=zonder` toont alleen rijen die in `samenvattingen` ontbreken. Pagina 2 houdt `filter=zonder` én `page=2`. phpMyAdmin:

```sql
SELECT g.id, g.onderwerp, MAX(a.publicatiedatum) AS nieuwste
FROM gebeurtenissen g
JOIN artikelen a ON a.gebeurtenis_id = g.id
LEFT JOIN samenvattingen s ON s.gebeurtenis_id = g.id
WHERE s.id IS NULL
GROUP BY g.id, g.onderwerp
HAVING COUNT(a.id) >= 2
ORDER BY nieuwste DESC, g.id DESC
LIMIT 15;
```

## Wel/geen per rij weg
De `@if` met “wel samenvatting” / “geen samenvatting” haalde ik weg. Het filter doet het onderscheid op lijstniveau.

Dat wijkt af van bouwblok 6: per gebeurtenis tonen of er al een samenvatting is. Op Alle zie ik dat niet meer; ik moet het onderwerp openen of eerst Met / Zonder kiezen. Bewust zo.

`withExists('samenvatting')` deed daarna niks meer. Die kolom `samenvatting_exists` werd alleen in die `@if` gelezen. Extra SQL zonder weergave, dus die regel uit de query. `has` / `doesntHave` in de `if` blijven: die filteren.

## Waarom ik het zo heb aangepakt
Eerst sorteren met `get()`, daarna de tiebreaker, daarna `paginate`, daarna het filter. Elke stap één concept (`withMax`, tweede `orderBy`, paginator, `Request` + `has`/`doesntHave`). Een mismatch met phpMyAdmin hoorde bij gelijke datums, niet bij een foute `withMax`.

## Beperkingen om te onthouden
- `publicatiedatum` heeft geen tijd. Binnen één dag beslist alleen `id`. (Sinds bouwblok 17 is het een `datetime`. De tiebreaker op `id` blijft voor gelijke tijden en voor oude artikelen die nog op `00:00:00` staan. Zie notitie 17.)
- `withCount('artikelen')` haalt `artikelen_count` nog op. De lijst toont dat totaal niet.
- Op Alle is niet zichtbaar welke rij een samenvatting heeft, tot ik filter of de detailpagina open.
- `paginate(15)` is een vaste paginagrootte, geen keuze in de UI.
- Filterlinks gaan naar `/gebeurtenissen`. De homepage `/` toont dezelfde `index`, maar zonder named route.
- Sinds bouwblok 14 klopt die laatste regel niet meer: `/` is een eigen homepage (`home`). Dezelfde `index` draait ook op `/onderwerpen/{categorie}`, met dezelfde sortering, paginering en filters. Het formulier stuurt dan naar die onderwerp-URL (`$lijstUrl`), zodat je op het onderwerp blijft. De query gebruikt nu scopes op het model (`zichtbaar()`, `voorKaart()`, `nieuwsteEerst()`) in plaats van de lange `has` / `withCount` / `withMax` in de controller. Op een onderwerppagina zonder filters staan bovenaan 3 trending gebeurtenissen, die uit de lijst zijn gehaald. Zie notitie 14.
