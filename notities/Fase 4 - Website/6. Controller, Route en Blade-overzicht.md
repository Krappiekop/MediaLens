#laravel #cheatsheet #medialens

Uitleg voor mezelf van wat ik gedaan heb bij bouwblok 6 van de MediaLens casus: een overzichtspagina van gebeurtenissen in de browser, via een route, een controller en een Blade-view.

## Controller in plaats van een closure
Tot nu toe zat in `routes/web.php` alleen de Laravel-welkomstpagina:
```php
Route::get('/', function () {
    return view('welcome');
});
```

Dat is een closure: de logica staat in de route zelf. Laravel-conventie voor een echte pagina: een controller. Artisan-commands stuurde ik zelf aan in de terminal. Een controller reageert op een HTTP-request in de browser.
```bash
php artisan make:controller GebeurtenisController
```

Dat zet `app/Http/Controllers/GebeurtenisController.php` neer. `index` is REST-conventie: toon de lijst. Eerste versie zonder database, om de keten te bewijzen:
```php
public function index()
{
    return 'Gebeurtenissen';
}
```

## Route koppelen
In `routes/web.php`:
```php
use App\Http\Controllers\GebeurtenisController;

Route::get('/gebeurtenissen', [GebeurtenisController::class, 'index']);
```

`Route::get` koppelt een GET-request aan een methode. `[Klasse::class, 'index']` is Laravel-array-syntax: welke class, welke methode. De `use` bovenaan is nodig, anders zoekt PHP de controller in de verkeerde namespace. Hetzelfde idee als `use` bij `ConnectionException` in het artisan-command.

De `/`-route laat ik nog op `welcome` staan. Eerst bewijzen dat `/gebeurtenissen` werkt.

Check of Laravel de route ziet:
```bash
php artisan route:list
```

Ik moet een regel zien: `GET gebeurtenissen` naar `GebeurtenisController@index`.

## Twee PHP's: Artisan vs Apache
Via XAMPP (`http://localhost/Educom/Cases/MediaLens/public/gebeurtenissen`) kreeg ik:
```
Composer detected issues in your platform: Your Composer dependencies require a PHP version ">= 8.4.1". You are running 8.2.12.
```

Artisan (`php artisan route:list`) werkte wel.

> [!warning] Op Windows staan vaak twee PHP's. De terminal pakt de PHP uit PATH (bij mij 8.4). De browser via XAMPP Apache draait 8.2.12. Composer checkt dat in `vendor/composer/platform_check.php` nog vóór Laravel start. Laravel 13 eist 8.4.1, dus de pagina crasht voordat `index()` draait.

Oplossing voor deze casus: de ingebouwde server, dezelfde PHP als Artisan:
```bash
php artisan serve
```

URL vanaf hier: `http://127.0.0.1:8000/gebeurtenissen`, niet meer `localhost/.../public/...`. phpMyAdmin via XAMPP blijft werken. Composer of `platform_check.php` aanpassen lost het niet op: Laravel 13 start alsnog niet op 8.2. Officiële XAMPP had bij mij geen 8.4-optie.

## Blade-view
Een platte string is geen pagina. Blade is Laravel’s templatesysteem: HTML in `resources/views`, extensie `.blade.php`.
```php
return view('gebeurtenissen.index');
```

Die regel hoort in de **controller**, als vervanging van `return 'Gebeurtenissen'`. Niet in `web.php`, niet in het Blade-bestand.

**Laravel-concept:** in `view('gebeurtenissen.index')` is `gebeurtenissen.index` geen URL. De punt is een map: `resources/views/gebeurtenissen/index.blade.php`. Hetzelfde als `config('services.litellm.model')`: punt = nesten.

Vanaf bouwblok 8 is de tekst `gebeurtenissen.index` óók een named route naar `/gebeurtenissen`. Zelfde woorden, twee betekenissen: de view-naam in `view()`, het route-label in `route()`. Zie notitie 8.

Eerste inhoud, nog zonder data:
```html
<!DOCTYPE html>
<html>
    <head>
        <title>Gebeurtenissen</title>
    </head>
    <body>
        <h1>Gebeurtenissen</h1>
    </body>
</html>
```

> [!warning] `view('gebeurtenissen.index')` zoekt alleen `resources/views/gebeurtenissen/index.blade.php`. Zet ik het bestand als `resources/views/index.blade.php`, dan hoort dat bij `view('index')`. Foutmelding: `View [gebeurtenissen.index] not found`. De controller kan dan wél kloppen.

## Onderwerpen uit de database
Queries horen in de controller, niet in Blade. De view toont HTML.
```php
use App\Models\Gebeurtenis;

public function index()
{
    $gebeurtenissen = Gebeurtenis::all();

    return view('gebeurtenissen.index', [
        'gebeurtenissen' => $gebeurtenissen,
    ]);
}
```

`Gebeurtenis::all()` kende ik van Tinker en de artisan-commands. Het tweede argument van `view()` is een array: de **key** wordt een variabele in Blade, de **value** is de collectie.

In de view, onder de `h1`:
```html
<ul>
    @foreach ($gebeurtenissen as $gebeurtenis)
        <li>{{ $gebeurtenis->onderwerp }}</li>
    @endforeach
</ul>
```

`@foreach` is Blade, geen PHP-`foreach` met `<?php`. `{{ }}` print én escaped HTML. Titels uit RSS kunnen gekke tekens hebben. `$gebeurtenis->onderwerp` is dezelfde kolom als in phpMyAdmin.

> [!tip] Status 200 of "er staat iets" is niet genoeg. Ik tel de regels en vergelijk onderwerpen met de tabel `gebeurtenissen` in phpMyAdmin. Lege lijst terwijl phpMyAdmin wél rijen heeft: dan praat `artisan serve` met een andere database. Check `DB_DATABASE` in `.env`.

## Aantal artikelen: withCount
Niet in de Blade-loop `$gebeurtenis->artikelen()->count()` doen. Dat is per rij een extra query (N+1). Bij 40 gebeurtenissen 40 extra counts.
```php
$gebeurtenissen = Gebeurtenis::withCount('artikelen')->get();
```

`withCount('artikelen')` gebruikt de `hasMany` uit bouwblok 1. Eloquent voegt `artikelen_count` toe via één SQL `COUNT`. `all()` mag hier niet: `withCount` bouw ik op de query, daarna `get()`.

In de `<li>`:
```html
<li>{{ $gebeurtenis->onderwerp }} ({{ $gebeurtenis->artikelen_count }} artikelen)</li>
```

Steekproef: phpMyAdmin, tabel `artikelen`, filter op `gebeurtenis_id`. Het getal in de lijst moet gelijk zijn.

## Filter: minstens twee artikelen
De casus-test voor bouwblok 6 zegt dat de lijst overeenkomt met de hele tabel `gebeurtenissen`, en dat rijen zonder samenvatting zichtbaar blijven. Groepen met 1 artikel staan in die tabel.

Ik filter toch op minstens 2 artikelen. Dat wijkt af van die 1-op-1-test, maar sluit aan op bouwblok 5: samenvatten doe ik pas vanaf `$minimaleArtikelen = 2`. Groepen met 1 artikel kunnen op dit overzicht nooit “af” zijn.

Filter in de **query**, niet in Blade. Anders haal ik alles op en gooi ik het daarna weg.
```php
$gebeurtenissen = Gebeurtenis::has('artikelen', '>=', 2)
    ->withCount('artikelen')
    ->get();
```

`has('artikelen', '>=', 2)` gebruikt dezelfde `hasMany`. Eloquent vertaalt dat naar SQL. `withCount` blijft nodig voor het getal in de view.

> [!note] `$gebeurtenis->artikelen_count >= 2` in `@foreach` is PHP-filteren ná het ophalen. `has()` filtert in de database.

Check: groepen met 1 artikel mogen niet in de lijst. Groepen met 2 of meer wél, ook zonder samenvatting.

## Of er een samenvatting is: withExists
`has('samenvatting')` zou **filteren**: alleen groepen mét een samenvatting. De casus wil het omgekeerde: zonder samenvatting blijven ze zichtbaar. `with('samenvatting')` laadt de hele rij (`kernfeiten`, `verschil`, enz.). Die teksten horen op de detailpagina, niet in deze lijst.

`withExists` is het ja/nee-broertje van `withCount`. Het gebruikt de `hasOne` uit bouwblok 1, filtert niet, en voegt `samenvatting_exists` toe via één SQL `EXISTS`.
```php
$gebeurtenissen = Gebeurtenis::has('artikelen', '>=', 2)
    ->withCount('artikelen')
    ->withExists('samenvatting')
    ->get();
```

**Laravel-concept:** de string `'samenvatting'` is de methodenaam van de relatie, niet de tabelnaam `samenvattingen`. Eloquent maakt daar `samenvatting_exists` van (relatienaam + `_exists`).

In Blade is `@if` dezelfde familie als `@foreach`: een directive, geen `<?php if`.
```html
<li>
    {{ $gebeurtenis->onderwerp }}
    ({{ $gebeurtenis->artikelen_count }} artikelen)
    @if ($gebeurtenis->samenvatting_exists)
        wel samenvatting
    @else
        geen samenvatting
    @endif
</li>
```

Check: een `gebeurtenis_id` die in `samenvattingen` staat moet “wel samenvatting” tonen. Een groep met 2+ artikelen zonder rij in `samenvattingen` moet in de lijst blijven, met “geen samenvatting”.

Sinds notitie 10 staat wel/geen niet meer per rij. Het filter Alle / Met / Zonder doet dat onderscheid. `withExists` is uit de query gehaald, omdat niets `samenvatting_exists` meer las. `has('samenvatting')` en `doesntHave('samenvatting')` filteren wél, zie notitie 10.

## Homepage naar dezelfde index
De closure op `/` toonde nog `welcome`. Twee routes mogen naar dezelfde controller-methode wijzen. `index()` kopieer ik niet.
```php
Route::get('/', [GebeurtenisController::class, 'index']);
Route::get('/gebeurtenissen', [GebeurtenisController::class, 'index']);
```

`/gebeurtenissen` blijft staan omdat bouwblok 7 `/gebeurtenissen/{gebeurtenis}` wordt. De naam `gebeurtenissen.index` op die URL komt in bouwblok 8. `/` blijft zonder naam. `welcome.blade.php` mag blijven liggen, hij wordt niet meer aangeroepen.

Check: `http://127.0.0.1:8000/` is dezelfde lijst als `/gebeurtenissen`. `php artisan route:list` toont twee `GET`-regels, beide naar `GebeurtenisController@index`.

## Waarom ik het zo heb aangepakt
Route wijst naar de controller, controller haalt data, Blade toont HTML. Zelfde scheiding als command vs matcher vs LiteLlm: elk stuk één verantwoordelijkheid.

Eerst een platte string, dan een lege view, dan onderwerpen, dan `withCount`, dan `has()`, dan `withExists`, dan `/` naar dezelfde `index`. Elke stap één Laravel-concept, zodat een foutmelding bij één ding hoort (PHP-versie, view-pad, query, filter vs exists).

## Beperkingen om te onthouden
- Filter op 2+ artikelen wijkt af van “lijst = hele tabel `gebeurtenissen`”. Groepen met 1 artikel staan in de database, niet op de pagina.
- Pagina’s draaien via `php artisan serve` (PHP 8.4). XAMPP Apache blijft 8.2 en start Laravel 13 niet.
- Aan het eind van dit bouwblok was de view kale HTML. De link naar de detailpagina staat in notitie 7. De gedeelde layout en Tailwind staan in notitie 8.
- `artikelen_count` wordt nog opgehaald. De lijst toont dat totaal niet meer. Sinds notitie 9 staat er de telling Links / Midden / Rechts.
- `withExists` en “wel/geen samenvatting” per rij horen bij dit bouwblok als leerconcept. In de huidige lijst zijn ze weg; het filter staat in notitie 10.

## Latere uitbreiding: nieuwskaarten (bouwblok 14)
De overzichtspagina is nu een nieuwsfeed met kaarten in plaats van een kale lijst. Per gebeurtenis zie ik de nieuwste publicatiedatum, het totale aantal artikelen en de aantallen Links / Midden / Rechts. De horizontale balk visualiseert dezelfde tellingen; de getallen blijven ernaast staan zodat kleur niet de enige informatiedrager is.

Als een gebeurtenis een artikel met `afbeelding_url` heeft, toont de kaart de afbeelding. De controller laadt daarvoor maximaal één artikel met afbeelding per gebeurtenis, met de nieuwste publicatiedatum eerst. De query neemt alleen de benodigde kolommen mee. Zonder afbeelding blijft de kaarttekst gewoon staan. Filters, paginering en links naar `gebeurtenissen.show` zijn behouden.

De vormgeving is geïnspireerd op een scanbare nieuwsfeed, niet letterlijk gekopieerd van Ground News. Zie `14. Visuele vormgeving en artikelafbeeldingen.md` voor de afbeeldingsquery, de verdelingsbalk en de visuele keuzes.
