#laravel #ollama #embeddings #medialens

Uitleg voor mezelf van bouwblok 16 van MediaLens: artikelen groeperen op betekenis met embeddings van een lokaal model (Ollama), in plaats van alleen op gedeelde RAKE-trefwoorden.

## Doel
RAKE met een drempel van 6 gedeelde trefwoorden was niet foolproof. Twee problemen:

- RAKE ziet geen synoniemen. `Israel strikes Gaza` en `IDF bombardment in Palestinian enclave` gaan over hetzelfde, maar delen geen enkel woord.
- De eerste kandidaat die de drempel haalde won, ook als er later een kandidaat kwam die veel beter paste.

De casus noemt embeddings + vectorsimilariteit als alternatief. Ik wilde dat proberen zonder betaalde API en zonder over te stappen op een andere database.

## Eerst: de beste kandidaat kiezen
Voordat ik aan embeddings begon, heb ik de RAKE-matcher aangepast. Eerst vergelijk ik alle kandidaten, daarna koppel ik aan de beste.
```php
$besteKandidaat = null;
$hoogsteOverlap = 0;

foreach ($kandidaten as $kandidaat) {
    $overlap = count(array_intersect($woordenNieuw, $this->trefwoordenVan($kandidaat)));

    if ($overlap >= $this->minimaleOverlap && $overlap > $hoogsteOverlap) {
        $besteKandidaat = $kandidaat;
        $hoogsteOverlap = $overlap;
    }
}
```

`>` en niet `>=`: bij een gelijke stand blijft de eerste kandidaat staan, net als vroeger.

## Wat is een embedding
Een embedding is een lijst getallen (een vector) die de betekenis van een tekst weergeeft. Teksten die over hetzelfde gaan, krijgen vectoren die dezelfde kant op wijzen, ook als ze andere woorden gebruiken. `nomic-embed-text` geeft 768 getallen per tekst.

Twee vectoren vergelijk ik met cosine similarity: hoe dicht ligt de richting bij elkaar.

- 1 = zelfde betekenis
- 0 = niets met elkaar te maken

```php
private function cosineSimilarity(array $a, array $b): float
{
    $inproduct = 0.0;
    $lengteA = 0.0;
    $lengteB = 0.0;

    foreach ($a as $index => $waarde) {
        $inproduct += $waarde * $b[$index];
        $lengteA += $waarde * $waarde;
        $lengteB += $b[$index] * $b[$index];
    }

    if ($lengteA == 0.0 || $lengteB == 0.0) {
        return 0.0;
    }

    return $inproduct / (sqrt($lengteA) * sqrt($lengteB));
}
```

## Ollama
Ollama is een programma dat taalmodellen lokaal draait. Het is geen VS Code-extensie: de Ollama-app draait op de achtergrond als een kleine webserver op `http://localhost:11434` (lama-icoontje in het systeemvak). Laravel praat er via de `Http`-facade mee, net als met LiteLLM in notitie 4.

Installeren op een nieuwe computer:
1. Installer downloaden van [ollama.com/download](https://ollama.com/download)
2. Model ophalen: `ollama pull nomic-embed-text` (±275 MB)
3. Controleren: `ollama list`

Zelf testen in PowerShell:
```powershell
Invoke-RestMethod -Method Post -Uri http://localhost:11434/api/embed -Body '{"model":"nomic-embed-text","input":"Hello world"}' -ContentType 'application/json'
```

> [!note] Werkt het niet, start dan "Ollama" via het startmenu of typ `ollama serve` in een terminal. De eerste aanroep duurt ±3 seconden, omdat het model dan in het geheugen wordt geladen. Daarna blijft het een paar minuten geladen.

## Service-klasse `Ollama`
Zelfde opzet als `LiteLlm`: config uit `config/services.php`, fail-fast als er iets ontbreekt, duidelijke `RuntimeException` bij een fout.
```php
$response = Http::timeout(120)
    ->post(rtrim($baseUrl, '/').'/api/embed', [
        'model' => $model,
        'input' => array_values($teksten),
    ]);
```

`input` mag een array zijn. Dan geeft Ollama in één antwoord een embedding per tekst terug. Dat is veel sneller dan per artikel een aanroep doen.

Config in `.env`:
```env
OLLAMA_BASE_URL=http://localhost:11434
OLLAMA_EMBEDDING_MODEL=nomic-embed-text
MATCHER_METHODE=embeddings
MATCHER_MINIMALE_SIMILARITY=0.85
```

> [!warning] Na een wijziging in `.env` eerst `php artisan config:clear`, anders leest Laravel nog de oude waarde uit de cache.

## Wat er naar het model gaat
```php
return trim('clustering: '.$artikel->titel.' '.implode(' ', array_slice($woorden, 0, 100)));
```

- Titel plus de eerste 100 woorden. Bij RAKE waren het 40, omdat promo-zinnen anders te veel gedeelde woorden gaven. Een embedding kijkt naar de hele betekenis en heeft daar minder last van.
- `clustering: ` vooraan vertelt `nomic-embed-text` waarvoor de vectoren bedoeld zijn: gelijke teksten groeperen. Het model is getraind met zulke voorvoegsels.

## Opslaan in MySQL
Laravel 13 heeft `whereVectorSimilarTo()`, maar dat werkt alleen op PostgreSQL met `pgvector`. Ik draai MySQL op XAMPP. Daarom sla ik de vector op als JSON:
```php
$table->json('embedding')->nullable();
```

In het model een cast, zodat ik er gewoon een PHP-array uit krijg:
```php
protected function casts(): array
{
    return [
        'embedding' => 'array',
    ];
}
```

Het vergelijken gebeurt in PHP. Dat kan, omdat de matcher alleen artikelen van dezelfde dag vergelijkt. Op de drukste dag zijn dat ±1.450 kandidaten × 768 getallen, en dat kost een paar tientallen milliseconden. (Sinds bouwblok 17 is het venster 48 uur, dus meer kandidaten per artikel. Nog steeds geen probleem in PHP.)

> [!note] JSON kent geen verschil tussen `1.0` en `1`. Wat ik als `[1.0, 0.0]` opsla, komt terug als `[1, 0]`. In de test daarom `assertEquals` en niet `assertSame`.

## Twee methodes naast elkaar
Met `MATCHER_METHODE` kies ik tussen `embeddings` en `rake`. Zo kan ik beide vergelijken.
```php
private function gebruiktEmbeddings(Artikel $artikel): bool
{
    return config('services.matcher.methode') === 'embeddings' && $artikel->embedding !== null;
}
```

Staat Ollama uit, dan vangt `maakEmbeddings()` de `ConnectionException` of `RuntimeException` op en schrijft een waarschuwing in de log. Het artikel heeft dan geen embedding, en `koppel()` valt terug op RAKE. `artikelen:ophalen` blijft dus werken.

## Volgorde in `artikelen:ophalen`
Vroeger: artikel aanmaken en meteen koppelen. Nu per bron in drie stappen:

1. Alle nieuwe artikelen van de bron aanmaken
2. Eén batch embeddings bij Ollama ophalen
3. Daarna elk artikel koppelen

Artikel 2 van dezelfde feed kan nog steeds aan artikel 1 gekoppeld worden, want artikel 1 krijgt eerst zijn gebeurtenis.

## Bestaande artikelen
`php artisan artikelen:embeddings` maakt embeddings voor artikelen die er nog geen hebben, per 50 tegelijk. Ik gebruik `lazyById(50)`, omdat die op `id` doorbladert. Ik pas tijdens het doorlopen namelijk de kolom aan waarop ik filter (`whereNull('embedding')`). Met gewone `offset`-paginering zou ik dan rijen overslaan.

Bestaande gebeurtenissen worden niet opnieuw gekoppeld. Dat zou de huidige groepen en samenvattingen overschrijven.

## Snelheid
| Wat | Tijd |
|---|---|
| Eerste aanroep (model laden) | ±3 s |
| Batch van 50 korte teksten | ±4 s |
| Backfill 4.206 artikelen | 9 min 42 s (±140 ms per artikel) |
| Per bron bij `artikelen:ophalen` | een paar seconden extra |

Dat is op de CPU van mijn laptop. Een betaalde API zou sneller zijn, maar Ollama is gratis en werkt zonder internet.

## De drempel kiezen
Ik heb alle artikelparen van dezelfde dag vergeleken. RAKE-paren = paren die RAKE al in dezelfde gebeurtenis had gezet; andere paren = een steekproef van paren uit verschillende gebeurtenissen.

| Drempel | RAKE-paren erboven | Andere paren erboven |
|---|---|---|
| 0,75 | 88,4% | 1,17% |
| 0,80 | 73,5% | 0,65% |
| 0,85 | 52,6% | 0,29% |

Die cijfers zijn geen waarheid: RAKE maakt zelf ook fouten. Daarom heb ik per niveau voorbeeldparen bekeken die RAKE in verschillende gebeurtenissen had gezet:

- **≥ 0,85**: meestal echt dezelfde gebeurtenis die RAKE miste (`Saudi airport struck again…` en `Saudi-led coalition says a projectile struck passenger terminal…`; twee stukken over de bootramp bij Djibouti)
- **0,80–0,85**: vooral hetzelfde onderwerp met een ander verhaal (twee verschillende Oekraïense drone-aanvallen)
- **< 0,80**: ander nieuws

Daarom staat de drempel op 0,85.

## Testen
```bash
php artisan test
```

Nieuwe tests:
- `ExampleTest`: artikelen met handmatig opgeslagen vectoren. De meest gelijkende kandidaat wint, en onder de drempel komt er een nieuwe gebeurtenis.
- `ArtikelenOphalenTest`: een feed met twee anders verwoorde artikelen. Ollama wordt nagebootst met `Http::fake()`. De test controleert dat de embedding is opgeslagen, dat beide artikelen in dezelfde gebeurtenis komen en wat er naar `/api/embed` is gestuurd.
- `ArtikelenOphalenTest`: Ollama onbereikbaar via `Http::failedConnection()`. Het command slaagt, het artikel heeft geen embedding maar wel een gebeurtenis via RAKE.

De tests praten nooit met de echte Ollama. `Http::preventStrayRequests()` in de bestaande feedtests geeft een `StrayRequestException`, en die is een `RuntimeException`. Daar valt de matcher dus ook netjes terug op RAKE.

## Latere uitbreiding: embeddings voor meer dan matchen (bouwblok 17)
Dezelfde vectoren worden nu voor drie dingen gebruikt:

- **Matchen**, zoals hierboven, maar binnen 48 uur in plaats van dezelfde dag.
- **De titel van een gebeurtenis.** Per artikel de cosine similarity met alle andere artikelen optellen; de titel van het artikel met de hoogste som wordt het `onderwerp`.
- **Gerelateerde gebeurtenissen.** Elke gebeurtenis krijgt het gemiddelde van de vectoren van haar artikelen (`gebeurtenissen.embedding`). De detailpagina toont de 3 gebeurtenissen die daar het meest op lijken, vanaf 0,8.

Bij dat laatste bleek dat het ophalen van 400 vectoren als JSON uit MySQL ±370 ms kost. Het rekenen zelf is snel. Het resultaat staat daarom een uur in de cache. Zie notitie 17.
