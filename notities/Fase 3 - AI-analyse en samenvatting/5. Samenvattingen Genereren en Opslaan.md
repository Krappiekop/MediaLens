#laravel #cheatsheet #medialens

Uitleg voor mezelf van wat ik gedaan heb bij bouwblok 5 van de MediaLens casus: een neutrale samenvatting laten maken, die in vier velden opslaan, en dat aansturen met een Artisan-command.

## Bestaande service uitbreiden
De README zei: bestaande AI-service uitbreiden, geen nieuwe HTTP-client. `LiteLlm::vraag()` blijft “stuur tekst, krijg tekst terug”. De nieuwe prompt en het opslaan horen in `ArtikelVergelijker`, want die kent al `artikelenTekst()` en de gebeurtenis-relatie.

Vier kolommen had ik in bouwblok 1 al in de migratie gezet: `kernfeiten`, `betrokkenen`, `overeenstemming`, `verschil`, plus `gebeurtenis_id`.

## Eerst vrije tekst, daarna JSON
Eerste versie van `samenvat()` vroeg vier kopjes als platte tekst. Zo kon ik lezen of het neutraal voelde, voordat ik ging parsen.

Daarna dezelfde vier stukken als JSON, met keys die hetzelfde heten als de databasekolommen. Dan is koppelen later 1-op-1.
```php
public function samenvat(Gebeurtenis $gebeurtenis): array
{
    $artikelen = $this->artikelenTekst($gebeurtenis);

    $prompt = "Hieronder staan nieuwsartikelen over dezelfde gebeurtenis.\n\n"
        . "Schrijf een neutrale samenvatting die begrijpelijk is voor een breed publiek.\n"
        . "Gebruik geen politieke labels en kies geen partij.\n"
        . "Noem bij de overeenstemming en verschil de namen van de bronnen.\n\n"
        . "Antwoord alleen met geldige JSON, zonder markdown, met precies deze keys:\n"
        . '{"kernfeiten":"","betrokkenen":"","overeenstemming":"","verschil":""}'
        . "\n\nArtikelen:\n\n"
        . $artikelen;

    $antwoord = (new LiteLlm)->vraag($prompt);
    $data = json_decode($antwoord, true);

    return is_array($data) ? $data : [];
}
```

`json_decode($antwoord, true)` maakt van JSON-tekst een PHP-array. `true` betekent associatief (`['kernfeiten' => '...']`), geen object. Als het model geen geldige JSON teruggeeft, krijg ik `[]` in plaats van een crash.

Oriëntatie geef ik nog steeds niet per artikel mee. In de prompt ook geen politieke labels. Anders schrijft het model die labels na in plaats van de tekst te lezen.

> [!note] Sommige modellen wikkelen JSON in ` ```json `. Dan is `json_decode` `null` en krijg ik een lege array. Flash deed dat bij mij niet. Als het later wel gebeurt, moet ik die fences eerst strippen.

## Opslaan en mass assignment
`Samenvatting` had nog geen `$fillable`. Zonder dat geeft `create()` weer een `MassAssignmentException`, hetzelfde als bij Artikel in bouwblok 2.
```php
protected $fillable = [
    'kernfeiten',
    'betrokkenen',
    'overeenstemming',
    'verschil',
    'gebeurtenis_id',
];
```

Eerste `slaOp()`: JSON-array pakken, `gebeurtenis_id` erbij, `create()`.
```php
$data = $this->samenvat($gebeurtenis);
$data['gebeurtenis_id'] = $gebeurtenis->id;

return Samenvatting::create($data);
```

Check in phpMyAdmin én via de `hasOne` uit bouwblok 1:
```php
App\Models\Gebeurtenis::find(5)->samenvatting
```

## Niet dubbel samenvatten
Een tweede `slaOp` op dezelfde gebeurtenis maakte eerst een extra rij. De casus wil: alleen samenvatten als er nog geen samenvatting is.
```php
if ($gebeurtenis->samenvatting) {
    return $gebeurtenis->samenvatting;
}
```

`$gebeurtenis->samenvatting` is de `hasOne`. Geen `null` betekent: er is al een rij, stop, geen LiteLLM-call. In Tinker is dat meteen klaar in plaats van 10 tot 30 seconden.

## Minstens twee artikelen
Overeenstemming en verschil hebben pas zin als er iets te vergelijken is. Drempel 2, niet 3: bij 3 sla ik te veel groepen over (matcher maakt ook groepen van twee). The Nation vult `left`; dat was eerder de reden om drempel 3 te overwegen.

Net als `$minimaleOverlap` in de matcher: één eigenschap, niet een magische `2` in de `if`.
```php
private int $minimaleArtikelen = 2;
```

`slaOp` kan daardoor niks teruggeven. Returntype `?Samenvatting`: model of `null`. Dat is PHP, geen Laravel.
```php
if ($gebeurtenis->artikelen()->count() < $this->minimaleArtikelen) {
    return $samenvatting;
}
```

`$gebeurtenis->artikelen()->count()` telt in SQL. De `()` is belangrijk: zo laad ik niet alle artikelen in het geheugen.

Telling ná “bestaat er al een samenvatting” in de eerste versie. In de uiteindelijke `slaOp` staat de telling eerst: te weinig artikelen geeft de bestaande samenvatting terug of `null`, en gaat niet naar de API.

## Opnieuw als er nieuwe artikelen zijn
Alleen “bestaat al, stop” is te streng. De casus vraagt: opnieuw samenvatten als er later artikelen bij komen.

Ik vergelijk de `created_at` van het nieuwste artikel met de `updated_at` van de samenvatting. Artikel nieuwer: `update()` op de bestaande rij, geen tweede rij.
```php
private function heeftNieuweArtikelen(Gebeurtenis $gebeurtenis, Samenvatting $samenvatting): bool
{
    $nieuwste = $gebeurtenis->artikelen()->max('created_at');

    return $nieuwste > $samenvatting->updated_at;
}
```

`max('created_at')` is één query. `update()` vult de rij en zet `updated_at` automatisch op nu. Daarom vergelijk ik `updated_at`, niet `created_at` van de samenvatting. Die laatste verandert bij een update niet.

Uiteindelijke volgorde in `slaOp`:
1. te weinig artikelen: bestaande rij of `null`
2. samenvatting bestaat én geen nieuwere artikelen: bestaande rij
3. samenvatting bestaat wél nieuwere artikelen: `update()`
4. nog geen samenvatting: `create()`

> [!warning] Een echte nieuwe RSS-item nabootsen met `$samenvatting->save()` werkt niet als test. `save()` zet `updated_at` zelf weer op nu, dus het artikel lijkt niet nieuwer. Wel via de query builder, die timestamps overslaat:
> ```php
> App\Models\Samenvatting::where('gebeurtenis_id', 3)->update(['updated_at' => now()->subYear()]);
> ```
> Daarna `php artisan samenvattingen:genereren 3` moet `vernieuwd` zeggen en naar LiteLLM gaan. Een tweede run meteen erna: `bestaat al`.

## Artisan-command
Zelfde idee als `artikelen:ophalen`: één commando, Laravel loopt de gebeurtenissen af.
```bash
php artisan make:command SamenvattingenGenereren
```

Attributes `#[Signature]` / `#[Description]` weer weghalen als Laravel die aanmaakt. Alleen `$signature` en `$description` houden.
```php
protected $signature = 'samenvattingen:genereren {gebeurtenis?}';
```

`{gebeurtenis?}` is een optioneel argument. `$this->argument('gebeurtenis')` is dan een id of `null`. Zonder id zou de eerste run elke groep van 2+ artikelen naar de API sturen. Eerst testen met één id:
```bash
php artisan samenvattingen:genereren 5
php artisan samenvattingen:genereren 3
```

In `handle()` moet ik **vóór** `slaOp` onthouden of er al een samenvatting was, en de oude `updated_at` als string:
```php
$bestaande = $gebeurtenis->samenvatting;
$oudUpdated = $bestaande?->updated_at?->toDateTimeString();
$samenvatting = $vergelijker->slaOp($gebeurtenis);
```

`$bestaande` en de returnwaarde kunnen hetzelfde object zijn. Na `update()` verandert `updated_at` op dat object. Als ik de oude waarde niet eerst als string vastleg, kan ik “bestaat al” en “vernieuwd” niet meer uit elkaar houden.

Vier meldingen:
- `null`: te weinig artikelen
- `$bestaande === null`: nieuw opgeslagen
- `updated_at` anders dan `$oudUpdated`: vernieuwd
- anders: bestaat al

`?->` is de nullsafe operator: als `$bestaande` `null` is, stopt PHP en wordt `$oudUpdated` `null`. Geen error op `->updated_at` van niks.

## Model wisselen zonder code
Eerst draaide ik op `Educom_Trainees_Smart_Router`. Van het traineeship kreeg ik daarna vaste OpenRouter-modellen, van goedkoop naar duur:

1. `openrouter/deepseek/deepseek-v4-flash`: kort, sentiment, goedkoop batchwerk
2. `openrouter/qwen/qwen3.8-flash`: standaard, o.a. samenvatting en NL-tekst
3. `openrouter/deepseek/deepseek-v4-pro`: zwaarder redeneren
4. `openrouter/google/gemini-3.8-flash`: escalatie, niet als default

`LiteLlm` leest `config('services.litellm.model')`, dus alleen `.env` aanpassen:
```env
LITELLM_MODEL=openrouter/deepseek/deepseek-v4-flash
```

Tinker of Artisan opnieuw starten, anders blijft het oude model in dat proces hangen. Flash was inhoudelijk prima voor deze JSON-samenvattingen, dus Qwen en Pro laat ik liggen tot Flash tekortschiet.

> [!tip] Groep 5 had al een samenvatting. `samenvattingen:genereren 5` zegt dan “bestaat al” en raakt het nieuwe model niet. Voor een echte testhit `samenvat()` in Tinker, of `updated_at` terugzetten zoals hierboven.

## Thinking, effort en temperature via .env
De body van `LiteLlm::vraag()` stuurde eerst alleen `model`, `messages` en `response_format`. DeepSeek V4 Flash vult de rest zelf in: thinking aan, effort `high`, temperature `1`.

Die drie knoppen staan nu in `.env`, dezelfde plek als het model. `LiteLlm` leest ze via `config()`, niet via `env()`. Leeg laten is de DeepSeek-standaard.

```php
$body = [
    'model' => config('services.litellm.model'),
    'messages' => $messages,
    'temperature' => config('services.litellm.temperature'),
    'thinking' => [
        'type' => config('services.litellm.thinking_type'),
    ],
    'reasoning_effort' => config('services.litellm.reasoning_effort'),
];
```

`thinking` is een object met `type`, zoals de DeepSeek-API het verwacht. `reasoning_effort` en `temperature` zijn losse velden.

Wat de knoppen doen bij deze samenvatting:

- `thinking.type`: `enabled` of `disabled`. Aan = eerst nadenken, daarna JSON. Uit = meteen het antwoord.
- `reasoning_effort`: `none` (thinking uit), `low`, `high` of `max`. Standaard `high`. `medium` wordt intern `high`, dus dat is geen echte test.
- `temperature`: 0 tot 2. Lager is vaster, hoger wisselt meer in formulering.

Belangrijk bij dit model: zolang thinking aan staat, heeft `temperature` geen effect. DeepSeek accepteert hem wel, zonder fout. `top_p` heeft bijna geen speelruimte (in thinking mode alleen 0,95 tot 1). `frequency_penalty` en `presence_penalty` doet DeepSeek niks meer mee.

Effort `max` kan langer duren dan `Http::timeout(60)`. Dan telt `samenvattingen:genereren` dat als een mislukte poging.

De aanroep gaat via LiteLLM naar OpenRouter (`openrouter/deepseek/deepseek-v4-flash`). Een veld dat DeepSeek kent, kan onderweg verdwijnen. Of het aankomt, zie ik aan de response: `choices.0.message.reasoning_content` gevuld betekent thinking aan. `usage.completion_tokens_details.reasoning_tokens` laat zien hoeveel tokens het nadenken kostte. Blijven tijd en `completion_tokens` gelijk terwijl ik effort verander, dan is de parameter onderweg gesneuveld.

Config controleren zonder een LLM-call:

```bash
php artisan config:clear
php artisan tinker --execute="dump(config('services.litellm.thinking_type'), config('services.litellm.reasoning_effort'), config('services.litellm.temperature'));"
```

Lege `.env`-regels horen `enabled`, `high` en `1` te geven. Daarna één waarde zetten, dump opnieuw, daarna weer leeg.

Vergelijken van kwaliteit: dezelfde gebeurtenis, één knop per keer. Eerst niks extra (baseline). Dan thinking uit, en pas daarna temperature op `0.3`. Effort `max` alleen als thinking uit een verschil tussen bronnen mist.

## Tokens, kosten en gebeurtenis_id loggen
De Chat Completions-response heeft al een `usage`-object. Extra API-call is niet nodig. Laravel-dot-notatie, hetzelfde als `choices.0.message.content`:

- `usage.prompt_tokens`: alles wat ik instuur (system + user). Dat is de input.
- `usage.completion_tokens`: wat het model teruggeeft. Dat is de output.
- `usage.prompt_tokens_details.cached_tokens`: deel van de input dat de provider herkent van een eerdere call.

`cached_tokens` is geen extra som. Als `prompt_tokens` 348 is en `cached_tokens` 314, dan zijn 314 uit de cache en 34 vers. Hoger is goedkoper. `0` betekent: de hele input is opnieuw gerekend. Output gaat nooit via die cache.

DeepSeek cacht automatisch op een gelijke prefix. Het vaste system-bericht staat daarom vooraan, de artikelen in het user-bericht. Hits zie ik vooral bij een retry of dezelfde gebeurtenis opnieuw. Verschillende gebeurtenissen blijven vaak op `0` of alleen dat kleine vaste deel, omdat de artikeltekst meteen afwijkt. `migrate:fresh` leegt de database, niet de cache bij de provider.

Prijzen komen uit `config('services.litellm.price_...')`, dus uit `.env` via `config/services.php`. `(int)` maakt van `null` een `0`, anders crasht de som als een veld ontbreekt.

```php
$promptTokens = (int) $response->json('usage.prompt_tokens');
$completionTokens = (int) $response->json('usage.completion_tokens');
$cachedTokens = (int) $response->json('usage.prompt_tokens_details.cached_tokens');

$verseInput = max(0, $promptTokens - $cachedTokens);

$kostenInput = ($verseInput / 1_000_000) * config('services.litellm.price_input');
$kostenCached = ($cachedTokens / 1_000_000) * config('services.litellm.price_cached');
$kostenOutput = ($completionTokens / 1_000_000) * config('services.litellm.price_output');
```

Zonder `$verseInput` zou ik cached tokens tegen het volle inputtarief rekenen, of twee keer. `/ 1_000_000` omdat de `.env`-prijzen per miljoen tokens staan. `1_000_000` is gewoon het getal 1000000; PHP mag die underscores.

`Log::info` schrijft naar `storage/logs/laravel.log`. `round(..., 6)` houdt kleine bedragen leesbaar. Per call is het vaak `0.0004`, geen hele euro’s. In de log kan PHP dat als `4.2e-5` zetten. Dat is hetzelfde getal.

`LiteLlm` mag geen Eloquent-model kennen. Het id geef ik mee als vierde argument, vanuit `samenvat()` die de gebeurtenis wél heeft:

```php
public function vraag(string $systeem, string $bericht, ?array $responseFormat = null, ?int $gebeurtenisId = null): string
```

```php
Log::info('llm usage', [
    'gebeurtenis_id' => $gebeurtenisId,
    'prompt_tokens' => $promptTokens,
    'completion_tokens' => $completionTokens,
    'cached_tokens' => $cachedTokens,
    'kosten_input' => round($kostenInput, 6),
    'kosten_output' => round($kostenOutput, 6),
    'kosten_cached' => round($kostenCached, 6),
    'kosten_totaal' => round($kostenInput + $kostenCached + $kostenOutput, 6),
]);
```

`?int $gebeurtenisId = null` mag ontbreken. `vergelijk()` is uitgecommentarieerd; die hoeft het id nu niet mee te geven.

Check: `php artisan samenvattingen:genereren 5` en in de log `gebeurtenis_id` naast de tokens. Verse input zelf natellen: `prompt_tokens - cached_tokens`, delen door een miljoen, keer `LITELLM_PRICE_INPUT`. Dat moet gelijk zijn aan `kosten_input`.

## Waarom ik het zo heb aangepakt
Eén `vraag()` voor bouwblok 4 en 5. De prompt en het opslaan zitten in `ArtikelVergelijker`. Het command stuurt alleen aan en print wat er gebeurde, net als het RSS-command de matcher aanroept maar zelf niet matcht.

Tokens en kosten logt `LiteLlm` zelf, want die ziet de HTTP-response. `ArtikelVergelijker` geeft alleen het `gebeurtenis_id` mee. Prijzen staan in `.env` naast het model, niet in de PHP-code.

JSON-keys gelijk aan kolomnamen scheelt een vertaallaag. `update()` in plaats van delete+create houdt hetzelfde `id` en dezelfde `hasOne`.

## Mislukte poging opnieuw, maximaal 3
Twee fouten stopten het command midden in de `foreach`.

Kapotte JSON: `samenvat()` geeft `[]` terug. `slaOp()` deed daarna toch `create()`. De tekstkolommen zijn NOT NULL, dus MySQL weigerde de insert.

Timeout: `Http::timeout(60)` gooit een `ConnectionException` in `LiteLlm::vraag()`. Die werd nergens gevangen.

`null` uit `slaOp()` betekent in het command al "te weinig artikelen". Een mislukte JSON-poging is daarom een exception, vóór `create()` en `update()`:

```php
foreach (['kernfeiten', 'betrokkenen', 'overeenstemming', 'verschil'] as $veld) {
    if (! isset($data[$veld]) || trim((string) $data[$veld]) === '') {
        throw new \RuntimeException("Ongeldige JSON van het model: veld {$veld} ontbreekt.");
    }
}
```

`isset` is false als `json_decode` niets bruikbaars opleverde, ook als het model de JSON in markdown wikkelt. `trim` vangt een veld met alleen spaties. De backslash voor `RuntimeException` is nodig: zonder die slash zoekt PHP de klasse in `App\Services`. Hetzelfde leerpunt als de `use` van `ConnectionException` in het RSS-command.

In `SamenvattingenGenereren` staat om `slaOp()` een lus van 3. Ik vang alleen `ConnectionException` (timeout) en `\RuntimeException` (ongeldige JSON). Een andere bug in mijn eigen code stopt het command nog steeds.

```php
use Illuminate\Http\Client\ConnectionException;

$samenvatting = null;
$gelukt = false;

for ($poging = 1; $poging <= 3; $poging++) {
    try {
        $samenvatting = $vergelijker->slaOp($gebeurtenis);
        $gelukt = true;
        break;
    } catch (ConnectionException | \RuntimeException $e) {
        $this->warn("{$gebeurtenis->id}: poging {$poging} mislukt ({$e->getMessage()})");
    }
}

if (! $gelukt) {
    $this->error("{$gebeurtenis->id}: overgeslagen na 3 pogingen");
    continue;
}
```

`$gelukt` begint op `false`. Alleen een `slaOp()` zonder exception zet hem op `true`. `break` stopt de pogingen-lus. De `foreach` over gebeurtenissen gaat daarna verder. `continue` slaat de meldingen `opgeslagen` / `vernieuwd` / `bestaat al` over voor deze gebeurtenis.

Te weinig artikelen is een gewone `return`, geen exception. Die gebeurtenis wordt niet drie keer geprobeerd.

`failed()` in `LiteLlm` geeft nog een lege string. Die loopt via de veldcheck en telt dus ook als een `RuntimeException`-poging. Een timeout blijft een `ConnectionException`, omdat `vraag()` die nog steeds niet zelf vangt.

Een mislukte poging schrijft niets: de exception valt vóór `create()` en `update()`.

Getest door tijdelijk `$data = [];` te zetten in plaats van `$this->samenvat($gebeurtenis)`. Per gebeurtenis die echt naar de API zou gaan: drie gele regels `poging mislukt`, daarna rood `overgeslagen na 3 pogingen`. Het command eindigt zonder stacktrace. Die tijdelijke regel daarna terugzetten. Met `$data = []` raak ik de timeout-tak niet. Die gebruikt dezelfde `catch`, maar een echte timeout duurt per poging tot 60 seconden.

## Prompt later: kernfeiten vs schrijfwijze
De eerste system-prompt vroeg een neutrale samenvatting, geen politieke labels, en bij overeenstemming/verschil de bronnamen. Het model ging dan feiten catalogiseren: “alle bronnen noemen 16:00 in de Bronx”, “Examiner noemt het strafblad, Guardian het kind”. Betrokkenen werd een zin als “ICE-agent en een man”.

Dat is niet wat ik op de detailpagina wil. Kernfeiten moet op zichzelf zeggen waar de gebeurtenis over gaat. Betrokkenen is een namenlijst met komma’s. Overeenstemming en verschil horen bij de schrijfwijze (toon, woordkeuze, nadruk, weglatingen), dichter bij `vergelijk()` uit notitie 4 dan bij een feitencheck.

Oriëntatie per artikel blijft uit de user-tekst, om dezelfde reden als in notitie 4. In `verschil` staat expliciet: geen labels als `left`, `right` of `neutral`. De AI kiest zelf geen partij. Dat wijkt af van de casuszin “neutrale samenvatting die laat zien waar bronnen van mening verschillen”, bewust: verschil is framing, niet extra feiten.

`$systeem` in `samenvat()` is nu:

```php
$systeem = "Hieronder volgen nieuwsartikelen over dezelfde gebeurtenis.\n\n"
    . "Schrijf in het Nederlands. Kies zelf geen partij.\n\n"
    . "kernfeiten: één zelfstandig leesbaar stuk. Begin met waar de gebeurtenis over gaat. "
    . "Daarna alleen de feiten die een lezer nodig heeft om het te begrijpen, zonder de artikelen te openen. "
    . "Geen bronnamen, geen analyse van toon.\n\n"
    . "betrokkenen: alleen namen en rollen, gescheiden door komma's. "
    . "Geen zinnen.\n\n"
    . "overeenstemming: analyseer de schrijfwijze, niet de gedeelde feiten. "
    . "Waar lijken toon, woordkeuze en nadruk op elkaar, ook over politieke verschillen heen? Noem bronnen bij naam.\n\n"
    . "verschil: analyseer hoe woordkeuze, nadruk en weglatingen de gebeurtenis kleuren. "
    . "Koppel dat aan hoe bronnen schrijven. Noem bronnen bij naam. "
    . "Gebruik geen labels als left, right of neutral.";
```

`json_schema` en `slaOp()` blijven hetzelfde. Alleen de instructie verandert.

Bestaande rijen blijven de oude tekst. `heeftNieuweArtikelen()` kijkt naar artikelen, niet naar de prompt. Rij in `samenvattingen` weg (niet de gebeurtenis), daarna `php artisan samenvattingen:genereren {id}`. Het vaste system-bericht is de cache-prefix: na deze wijziging is `cached_tokens` eerst weer laag tot dezelfde nieuwe prompt terugkomt.

Check op de ICE-gebeurtenis (man neergeschoten in de Bronx): kernfeiten zonder bronnamen en met een openingszin over wat er gebeurde; betrokkenen als kommagescheiden namen (kind, DHS, Mamdani als ze in de teksten staan); overeenstemming over toon, niet over de kloktijd; verschil over termen als `illegal` vs `undocumented` en wat extra nadruk krijgt.

## Beperkingen om te onthouden
- Input is nog steeds de RSS-omschrijving, geen volledige artikeltekst.
- Gemengde groepen (ketting-matching) maken ook de samenvatting onbruikbaar.
- Na 3 mislukte pogingen blijft die gebeurtenis zonder (nieuwe) samenvatting tot een volgende run.
- Alleen `ConnectionException` en `RuntimeException` worden herhaald. Een andere exception stopt het command.
- `LiteLlm::vraag()` vangt een timeout nog steeds niet zelf. Het command doet dat.
- Flash is goedkoop en snel, geen garantie dat elke run even sterk is.
- `.env.example` en `LITELLM_MODEL` noemen nu allebei `openrouter/deepseek/deepseek-v4-flash`. Die twee gelijk houden als het model wisselt. De `PRICE_`-regels horen bij datzelfde model.
- Thinking aan (standaard) maakt temperature nutteloos. Eerst thinking uitzetten als ik formulering wil vastzetten.
- Of `thinking` / `reasoning_effort` de proxy haalt, zie ik niet aan HTTP 200. Wel aan `reasoning_content` of `reasoning_tokens`.
- Token- en kostencijfers zijn een schatting van wat de provider teruggeeft, geen factuur. Cached tokens niet bij `prompt_tokens` optellen: ze zitten er al in.
- De kosten staan in de log, nog niet in de artisan-output. `vraag()` geeft nog steeds alleen de tekst terug.
- Overeenstemming/verschil vragen nu om schrijfwijze, niet om een feitencatalogus. Het model kan alsnog feiten opsommen; dan is de prompt te ruim, niet de JSON-schema.
- Een promptwijziging raakt bestaande samenvattingen niet tot ik de rij weghaal en opnieuw genereer.
- Dat het model geen neutrale arbiter is, staat sinds notitie 11 ook op `/over` en in `ONTWERPKEUZES.md` onder Transparantie, niet alleen hier.
- Sinds bouwblok 14 heeft het `json_schema` een vijfde verplicht veld: `categorie`, als `enum` uit `App\Categorie`. `slaOp()` zet dat op de gebeurtenis, niet in `samenvattingen`, en een onbekende waarde telt als mislukte poging. Oude samenvattingen krijgen zo geen categorie (`heeftNieuweArtikelen()` slaat ze over); daarvoor is `gebeurtenissen:categoriseren`. Zie notitie 14.
