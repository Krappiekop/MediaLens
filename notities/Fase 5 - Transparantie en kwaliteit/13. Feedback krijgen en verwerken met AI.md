#laravel #cheatsheet #medialens

Uitleg voor mezelf van wat ik gedaan heb bij bouwblok 13 van de MediaLens casus: feedback krijgen en verwerken met AI, en dat gebruiken om de app op basis van echte signalen te verbeteren.

## Waarom dit het eerste AI-bouwblok is
Dit is het eerste bouwblok dat ik bewust met behulp van AI heb opgebouwd in plaats van alleen met mijn eigen code-gevoel. De reden is dat de applicatie al een stevige basis had, maar dat er nog een aantal kritieke risico's zichtbaar waren:

- een van de eerste tests faalde in de lokale testomgeving
- de homepage had een database- en setupprobleem in de in-memory SQLite-testomgeving
- de AI-service gaf te weinig duidelijke fouten terug als de proxy faalde
- de detailpagina was fragiel bij lege of incomplete gegevens
- de AI-output kon ongestructureerd of verkeerd getypt terugkomen, zonder dat de app dat expliciet afwees

In plaats van blind te repareren, heb ik met AI eerst de code, README en notities vergeleken met de werkelijke projectbehoefte, daarna de echte oorzaken opgespoord en pas daarna gerichte fixes gemaakt.

## De workflow in plaats van “blind aanpassen”
Ik heb de AI niet gebruikt om zomaar code te schrijven, maar om een reviewloop te maken:

1. De opdracht lezen in `README.md`
2. De notities doorlopen per bouwblok
3. De code beoordelen op echte risico's
4. Een concrete oorzaak identificeren
5. Een kleine, gerichte fix toepassen
6. De wijziging verifiëren met de relevante tests

De kern van deze workflow is: AI als reviewer en hardening-partner, niet als automatisch “magische” fix.

## Stap 1: de testomgeving terug op orde brengen
De eerste grote fout zat in de basis van de app: een homepage-test gaf 500. De oorzaak was niet de route zelf, maar het feit dat de testdatabase niet goed werd gebouwd.

```php
use Illuminate\Foundation\Testing\RefreshDatabase;

class ExampleTest extends TestCase
{
    use RefreshDatabase;
}
```

Dat is belangrijk, omdat Laravel bij tests standaard een SQLite in-memory database gebruikt. Zonder `RefreshDatabase` bestaan de tabellen niet, en dan crashen routes die data queryen direct.

De eerste fix was dus niet een controller-fix, maar een test-setup-fix.

## Stap 2: mass assignment goedzetten
Na de testopzet kreeg ik een andere fout: een model kon niet worden gevuld met data in de test.

```php
class Bron extends Model
{
    protected $table = 'bronnen';

    protected $fillable = [
        'naam',
        'orientatie',
    ];
}
```

Dit was nodig omdat `Bron::create([...])` in de test Laravel anders blokkeerde met een mass assignment error. De model moest expliciet vertellen welke velden veilig ingevuld mogen worden.

## Stap 3: echte app-flow testen in plaats van alleen 200-status
Ik heb daarna niet alleen een standaard homepage-test laten staan, maar ook meer realistische route-tests toegevoegd.

```php
public function test_the_gebeurtenissen_overview_loads_with_sample_data(): void
{
    $bronA = Bron::create([...]);
    $bronB = Bron::create([...]);

    $gebeurtenis = Gebeurtenis::create([
        'onderwerp' => 'Testgebeurtenis met twee artikelen',
    ]);

    Artikel::create([...]);
    Artikel::create([...] );

    $response = $this->get('/gebeurtenissen');

    $response->assertOk();
    $response->assertSee('Testgebeurtenis met twee artikelen');
}
```

Het doel hiervan is dat je niet alleen controleert of de route boot, maar ook of het overzicht echt data kan renderen zonder crashen.

## Stap 4: AI-fouten zichtbaar maken
Het reviewpunt dat het grootste risico vormde, was de LLM-call. In de oorspronkelijke code werd een proxyfout stilletjes omgezet naar een lege string. Dat maakt debugging moeilijk, omdat de app dan later “gewoon verder gaat” met een lege response.

De fix was om expliciet te falen bij een slechte response:

```php
if ($response->failed()) {
    throw new \RuntimeException(
        "LLM call failed with HTTP {$response->status()}: {$errorMessage}"
    );
}
```

Daarna ook:

```php
if ($content === '') {
    throw new \RuntimeException('LLM response was empty or missing content.');
}
```

En een fail-fast check voor configuratie:

```php
if ($baseUrl === '' || $apiKey === '' || $model === '') {
    throw new \RuntimeException(
        'LLM-configuratie ontbreekt: base_url, api_key en model zijn verplicht.'
    );
}
```

Dat is cruciaal voor een app die afhankelijk is van een externe AI-service. Zonder deze checks zie je later alleen een vage fout, in plaats van een duidelijke oorzaak.

## Stap 5: detailpagina robuust maken
De detailpagina kon nog crashen als een gebeurtenis geen artikelen had, of als een artikel geen bron of orientatie had. De fix was om dat veilig te verwerken in de controller en de view.

```php
$artikelen = $gebeurtenis->artikelen ?? collect();

$artikelenPerOrientatie = $artikelen->groupBy(function ($artikel) use ($bakjes) {
    $orientatie = $artikel?->bron?->orientatie;

    if ($orientatie === null || $orientatie === '') {
        return 'Onbekend';
    }

    return $bakjes[$orientatie] ?? $orientatie;
});
```

Daarna werd een extra bakje `Onbekend` toegekend en de Blade-view aangepast om een ontbrekende bron veilig te tonen met een fallback, zodat de pagina ook bij incomplete data blijft renderen.

## Stap 6: AI-output strikter valideren
De volgende verbetering was niet meer “proxyfout zichtbaar maken”, maar “AI-output ook type-veilig accepteren”. De app had nog een zwakke plek: `json_decode()` gaf data terug, maar `slaOp()` accepteerde ook arrays of lege waarden zonder verder te controleren.

Daarom is de validatie aangescherpt:

```php
foreach (['kernfeiten', 'betrokkenen', 'overeenstemming', 'verschil'] as $veld) {
    if (!array_key_exists($veld, $data) || !is_string($data[$veld]) || trim($data[$veld]) === '') {
        throw new \RuntimeException("Ongeldige JSON van het model: veld {$veld} ontbreekt of is geen tekstveld.");
    }
}
```

Dat is belangrijk, omdat een LLM berekeningen niet altijd in de exacte verwachte vorm teruggeeft. Door die validatie expliciet te eisen, voorkom je dat de app valse samenvattingen opslaat onder het mom van “goed nieuws”.

## Stap 7: retrylogica en onverwachte fouten beter afhandelen
De command `samenvattingen:genereren` is ook aangescherpt. Niet meer “alle fouten op dezelfde manier” behandelen, maar duidelijk:

- `ConnectionException` => retrybaar
- `RuntimeException` => retrybaar in het geval van ongeldige JSON of lege output
- onverwachte `Throwable` => direct loggen en stopzetten met duidelijke foutmelding

Daarmee heb je een command die robuuster is tegen echte productie-omstandigheden, zonder stilzwijgend door te draaien met een corrupte of onvolledige samenvatting.

## Stap 8: same-day matching harden
Naast de AI-hardening is er ook een echte data-regel verbeterd: artikelen mogen alleen nog aan elkaar worden gekoppeld als ze op dezelfde kalenderdatum vallen. De vorige `±1 dag`-regel was te breed en kon een verhaal dat de volgende dag opnieuw werd behandeld alsnog als dezelfde gebeurtenis groeperen.

De matcher gebruikt nu een strikte same-day check:

```php
$zelfdeDatum = Carbon::parse($artikel->publicatiedatum)->toDateString();

$kandidaten = Artikel::where('id', '!=', $artikel->id)
    ->whereNotNull('gebeurtenis_id')
    ->whereDate('publicatiedatum', $zelfdeDatum)
    ->get();
```

Dat voorkomt dat een “nieuw” onderwerp op de volgende dag per ongeluk in dezelfde gebeurtenis belandt.

> [!note] In bouwblok 17 is deze regel teruggedraaid naar een venster van 48 uur. Toen kon dat wel: `publicatiedatum` had een tijd gekregen (dus geen middernachtsgrens meer), en sinds bouwblok 16 kiest de matcher met embeddings de beste kandidaat in plaats van de eerste. Het risico waar deze stap tegen beschermde is daardoor kleiner. Zie notitie 17.

## Stap 9: tests voor edge cases
Na elke fix heb ik een test toegevoegd voor de fout die we net oplosten. Niet alleen voor het happy path, maar ook voor de edge cases die in een AI- en data-app veel belangrijker zijn:

- homepage 200
- overzichtspagina met echte data
- proxyfout op LLM
- ontbrekende LLM-configuratie
- detailpagina zonder artikelen
- artikel zonder bron in de view
- ongeldige AI-output in `ArtikelVergelijker`

Dat is het verschil tussen “code die werkt op mijn machine” en “code die fijne, kleine risico’s echt onder controle heeft”.

Daarmee was deze AI-feedbackloop niet alleen theoretisch, maar daadwerkelijk bewezen in de projectcode.

## Waarom dit bouwblok belangrijk is
Dit is het eerste bouwblok dat echt laat zien hoe AI mij heeft geholpen om de app beter te maken, niet om sneller een oplossing te verzinnen. De workflow was:

- eerst de code en context begrijpen
- dan de echte oorzaken isoleren
- kleine, doelgerichte hardening fixes toepassen
- daarna testen en reviewen

Die loop is precies wat ik in de rest van het project ook wil blijven gebruiken: feedback krijgen, verwerken, testen, en alleen dan doorbouwen naar de volgende stap.
